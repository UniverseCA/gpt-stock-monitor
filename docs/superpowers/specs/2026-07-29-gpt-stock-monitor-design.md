# GPT 号源监控项目设计

**日期：** 2026-07-29

**状态：** 已完成独立审查并修复最终审查意见，等待用户审阅

**目标：** 面向已配置的 `pay.ldxp.cn` 店铺分类，构建一个开源监控工具

## 1. 项目目的

构建一个可靠、易维护的开源项目，定期检查配置的
`pay.ldxp.cn/shop/<店铺ID>` 页面，发现商品和库存变化。首个部署目标为
GitHub Actions，每 5 分钟运行一次，并通过飞书自定义机器人 Webhook 发送提醒。

本项目只负责报告页面变化，不会自动购买商品、绕过访问控制，也不保证用户打开链接时
商品仍然有货。

## 2. 已确认的范围

首个版本将支持：

- 仅支持 `pay.ldxp.cn` 店铺；
- 支持配置一个或多个店铺，并为每个店铺配置一个或多个分类名称；
- 提供示例配置，默认分类为 `GPT-plus成品号`；
- 使用 Python 3.12、Playwright 和 Chromium；
- 通过 GitHub Actions 每 5 分钟定时运行，也支持手动触发；
- 通过飞书 Webhook 发送通知；
- 第一次成功运行时静默建立基线，不发送大量“新增商品”提醒；
- 识别新增商品、商品下架、库存状态变化、库存文案变化、价格变化和商品名称变化；
- 在独立的 `monitor-state` 分支保存语义快照和通知投递记录；
- 支持 `dry-run` 试运行模式，只报告差异，不发送消息，也不修改状态。

首个版本不包含网页管理后台、数据库、账号登录、代理池、自动购买、任意网站抓取或多个
通知渠道。

## 3. 选定的实现方式

使用 Playwright 模拟普通浏览器加载店铺页面，等待页面及其 JavaScript 检查完成，通过
页面可见名称选择分类，并解析渲染后的商品卡片。

与直接调用未公开的店铺接口相比，该方案更适合当前网站：普通 HTTP 请求目前只会获得
JavaScript 验证页面。与截图对比相比，解析语义化 DOM 数据能更准确地指出哪个商品、
哪个字段发生了变化，并减少误报。

项目不会尝试破解交互式验证码或其他访问控制。如果页面要求人工验证，本次运行必须明确
失败，并保留最后一次已知正确的状态。

## 4. 系统架构

实现将拆分为职责清晰的小组件：

- `cli.py`：提供单次监控命令和 `--dry-run` 行为；
- `config.py`：读取并校验 YAML 配置；
- `models.py`：定义标准化的店铺、分类、商品、快照和变化模型；
- `monitor.py`：编排监控流程，并使每个店铺相互独立；
- `diff.py`：在不依赖浏览器和网络的情况下比较两个语义快照；
- `state.py`：读取和写入确定性的 JSON 状态；
- `notifiers/feishu.py`：生成并发送飞书 Webhook 消息；
- `sites/ldxp.py`：集中处理 `pay.ldxp.cn` 的浏览器导航和 DOM 解析。

所有网站特有行为必须限制在网站适配器内。店铺页面结构变化时，不应影响差异比较、状态
存储或通知模块。

## 5. 配置设计

仓库将包含已提交的 `config/monitors.yaml`，其中放置不含秘密信息的示例店铺和默认分类。
Fork 项目的用户直接编辑该文件，选择需要监控的店铺和分类。飞书 Webhook 不得写入
YAML，而应从 `FEISHU_WEBHOOK_URL` 环境变量读取，并由 GitHub Actions Secret 提供。

每个监控配置包含：

- 稳定且唯一的本地监控 ID；
- 用于展示的名称；
- 形如 `https://pay.ldxp.cn/shop/<店铺ID>` 的网址；
- 至少一个需要监控的精确分类名称；
- 只有在实际验证表明默认值不足时，才允许配置页面超时参数。

配置校验必须拒绝不支持的域名、重复的监控 ID、空分类、格式错误的网址和未知字段。
店铺网址必须使用 HTTPS，主机名必须精确等于 `pay.ldxp.cn`，使用默认端口，不得包含
用户凭据、查询参数或片段，并且路径必须精确匹配 `/shop/<店铺ID>`。每次导航或重定向
完成后，还必须使用相同规则重新校验最终网址。每 5 分钟运行一次的计划只定义在工作流
中，不在应用配置中重复定义。

## 6. 商品模型与标准化

对于每个已渲染的商品卡片，适配器必须从 DOM 属性中的商品 ID 或规范商品链接中提取
稳定标识。名称、价格、库存文案、图片网址和卡片位置等可变字段不得作为商品标识。

如果某张商品卡片无法取得稳定标识，则该分类本次解析应判定为异常，并禁止覆盖原状态。
因此，只有在商品具有稳定 ID 或规范链接时，系统才保证能够识别改名和改价。该要求是
适配器必须遵守的不变量，也必须由测试样本验证。

快照按照监控 ID 和分类名称组织，其中每个商品包含：

- 稳定商品键；
- 可用时保存规范商品链接；
- 标准化后的名称；
- 标准化后的价格表示及原始展示文本；
- 标准化后的库存状态，例如 `in_stock`、`low_stock`、`out_of_stock`
  或 `unknown`；
- 原始库存文案。

比较前应统一处理空白和无意义的格式差异。写入 JSON 前，商品按稳定商品键排序，避免
页面排序变化被误报为商品变化。时间戳不得参与语义比较；除非作为独立元数据确有需要，
否则也不写入状态提交。

## 7. 变化检测

纯差异比较层将产生以下类型的变化：

- 新增商品；
- 商品下架；
- 库存状态变化，包括缺货变为有货和有货变为缺货；
- 当标准化状态不足以表达变化时，报告库存文案变化；
- 价格变化；
- 商品名称变化。

每次运行的变化汇总为飞书消息，并按店铺和分类展示。每项变化包含当前商品名称、相关的
变化前后值、可用时附带商品链接，并使用亚洲/上海时区记录检查时间。

某个“监控 ID + 分类”的第一次成功且非空的快照只用于建立基线，不发送商品变化通知。
只有当页面明确显示分类商品数为零，并且连续两次运行都观察到零时，才接受空分类结果。
第一次观察到零时保留旧商品快照。第二次确认后：如果该分类原来有商品，则产生商品下架
事件；如果是新分类，则静默建立空基线。

如果解析到零张卡片，但页面没有可信的零商品计数，或页面显示的计数不为零，本次解析
始终判定为异常。已从配置文件删除的监控项会在配置校验后从状态中静默删除；以后重新
加入时，将重新建立基线。

## 8. 单次运行流程

每次运行按以下流程执行：

1. 在启动浏览器前读取并校验配置。
2. 从状态工作树读取最后一次已知正确的快照、空分类候选状态、健康状态和投递记录。
3. 如果启用了 `dry-run`，跳过所有待发送消息和状态发布；只在输出中记录经过脱敏的
   待发送事件 ID 及数量，然后继续执行只读的抓取和差异比较。
4. 非 `dry-run` 模式下，在抓取前按时间顺序发送已有的待处理事件，并使用其中保存的
   不可变消息分片。如果发送失败，以退出码 3 结束，不抓取页面，也不推进监控状态。
   所有待处理事件发送完成后，从远端状态分支重新加载状态。
5. 启动一个 Chromium 进程，并串行访问已配置的店铺。
6. 对每个店铺，等待页面验证和商品内容稳定。
7. 通过可见名称找到每个配置的分类，并解析商品卡片。
8. 校验解析结果、标准化商品并创建新快照。
9. 将每个成功快照与其上一次快照比较。
10. 在 `dry-run` 模式下，将脱敏后的结构化差异和待处理事件摘要输出到标准输出，然后
    结束，不发送通知，也不修改状态。
11. 如果本次没有需要通知的内容，则以原子方式发布必要的基线、健康状态、空分类候选
    或配置清理变化。如果确实没有任何状态变化，则不创建提交。
12. 如果需要发送商品变化、异常或恢复通知，则根据上一次状态提交和标准化变化生成
    确定性的事件 ID。以原子方式提交并推送新快照，同时写入一条 `pending` 记录；该
    记录包含不可变且不含秘密信息的飞书消息分片。
13. 按顺序发送这些已保存的消息分片。只有全部分片发送成功后，才将该事件标记为
    `delivered` 并推送；否则保留已提交的待处理事件和已推进的快照，供下次启动时重试。

一个店铺失败不应阻止其他店铺继续检查。每次状态发布都对应一个原子的 Git 提交；一次
需要通知的运行通常先创建一个待处理事件提交，再创建一个标记为已送达的提交。失败或
可疑的解析结果不得替换最后一次已知正确的商品快照。

## 9. 异常处理与提醒去重

页面导航和解析最多重试 3 次，并逐步增加等待时间。重试必须有明确上限，避免一次
Actions 运行无限延长并与下一次计划任务重叠。

以下情况属于监控异常，不属于商品变化：

- 页面导航超时或无法恢复的浏览器错误；
- 出现交互式验证或验证码；
- 找不到配置的分类；
- 未观察到可信的分类商品数为零，却解析到零张商品卡片；
- 商品标识格式错误或重复；
- 飞书发送失败。

异常状态与商品状态分开保存，并以“监控 ID + 分类”为键。店铺级导航失败会使该店铺
配置的每个分类分别增加一次失败计数；分类级失败只影响对应分类，因此同一店铺内成功的
其他分类仍可恢复或更新。

在连续失败第 1 次、第 3 次以及此后每 12 次失败时创建异常提醒。发生一次或多次失败后，
第一次成功解析会重置计数并创建一条恢复提醒。第一次尚未确认的明确零商品结果会记录为
空分类候选，它在健康状态上属于成功观察，但不会替换商品快照。“连续两次”是指该分类
连续两次成功观察到明确的零商品计数；中间出现任何解析失败都会清除该候选状态。以上
序列必须通过样本测试验证。飞书发送失败会保留待处理事件，并使工作流明确失败。

日志可以记录监控 ID、分类名称、重试次数和脱敏后的错误详情，但不得输出 Webhook
网址、Cookie、Secret 或完整的敏感响应头。

## 10. 状态分支规则

定时工作流检出触发运行的主分支代码提交，然后在独立的临时 Git 工作树中挂载
`monitor-state`。如果该分支不存在，工作流创建一个孤儿工作树，其中只包含状态格式标记
和初始状态。该分支保存确定性的 JSON 商品快照、空分类候选、健康状态和投递记录，不得
保存凭据或 Cookie。

只有当商品语义、健康状态、空分类候选或投递状态变化时，工作流才创建提交。工作流使用
仓库范围的 `GITHUB_TOKEN`，权限仅开放 `contents: write`，其他权限只读或关闭。定时
运行和手动运行共用固定并发组 `gpt-stock-monitor`，并设置
`cancel-in-progress: false`。

每次推送状态前，发布器必须获取远端分支，并确认预期父提交仍然是远端最新提交。禁止
强制推送。在不重新运行浏览器的前提下，状态发布最多重试 3 次：

- 发送通知前如果发生冲突，只有当刷新后的状态中不存在待处理事件时，才能使用已经观察
  到的页面结果重新计算基线、健康状态、快照和事件变化。如果发现任何待处理事件，则
  丢弃当前观察结果，并以退出码 3 结束，让下次运行先完成待处理工作，再重新抓取页面。
  待处理提交被确认已存在于远端之前，不得发送消息；
- 发送通知后如果发生冲突，则重新加载状态并核对同一事件 ID。如果事件已标记为送达，
  当前阶段视为成功；否则只重试写入送达标记；
- 如果 3 次重试全部失败，则以退出码 3 结束。已经确认的待处理事件将成为恢复来源，
  下次运行按照“至少一次”的规则重新发送其已保存的消息内容。

一个 Git 提交是跨全部状态文件的原子发布单位。

通知采用“至少一次”投递语义，因为飞书和 Git 之间无法构成一个分布式事务。下次运行
必须先处理旧的待处理事件，之后才能抓取页面或创建新事件。待处理记录保存排序后的、
不可变的消息分片，不依赖已推进的快照重新计算差异。如果飞书已经接受消息，但记录发送
进度或最终 `delivered` 标记失败，该消息分片可能被再次发送。每条消息都包含确定性的
事件 ID，便于识别和测试重复投递。

如果分支保护或 Fork 项目权限阻止状态推送，工作流必须给出清晰的设置错误并失败。
README 应说明所需的 Actions 权限和首次创建状态分支的流程。

## 11. GitHub Actions 设计

`monitor.yml` 包含：

- 使用 `*/5 * * * *` 的定时计划；
- 支持传入试运行选项的 `workflow_dispatch` 手动触发；
- 最小权限设置，仅允许写入仓库内容；
- 不会取消正在运行任务的固定并发组；
- Python 和 Playwright 浏览器安装，并在有价值时使用依赖缓存；
- 明确的任务超时；
- 禁止带有飞书 Secret 的任务由不受信任的 Pull Request 触发。

适配器只使用普通 Playwright Chromium。禁止使用隐身补丁、验证码破解、验证令牌提取、
代理轮换、登录或跨运行持久化 Cookie。遇到交互式验证，或最终网址跳转到校验范围以外，
必须作为终止性的监控异常处理。

GitHub 不保证 Cron 精确按时执行，公共仓库尤其可能延迟，因此 README 必须说明这是
“每 5 分钟尽力执行”。`ci.yml` 在推送和 Pull Request 时运行，不使用 Secret，也不
访问真实店铺。

## 12. 测试与质量门禁

测试使用经过脱敏的本地 HTML 样本和模拟的飞书响应。CI 不得依赖真实店铺。

必须包含以下自动化测试：

- 有效和无效配置；
- 建立基线时不发送通知；
- 商品新增和下架；
- 补货和售罄；
- 仅库存文案发生变化；
- 价格和名称变化；
- 页面商品排序和空白变化不产生差异；
- 防止空解析覆盖状态；
- 找不到分类和识别验证页面；
- 一个店铺失败后其他店铺仍继续执行；
- 聚合通知和 Secret 脱敏；
- 飞书失败后保留已提交的待处理事件和已推进的快照，但不标记为送达；
- 商品改名或改价时保持稳定标识，并拒绝没有稳定标识的商品卡片；
- `dry-run` 不产生任何外部操作或状态修改；
- 状态序列化结果确定且稳定。

状态机测试还必须覆盖：静默基线发布、无变化时不创建提交、从不可变的多分片内容按时间
顺序重试、先处理旧事件再开始新监控、存在待处理事件时 `dry-run` 仍完全只读，以及在
创建待处理事件和标记送达两个阶段发生预期父提交冲突，包括冲突后发现更早待处理事件的
情况。

只有在 HTTP 响应成功，并且 JSON 响应体包含文档规定的成功码（`code: 0` 或旧版
`StatusCode: 0`）时，飞书发送才算成功。消息超过保守的载荷限制时，应在变化项目边界
拆分，并让每个分片都包含相同的事件 ID 和 `当前分片/总分片`。只有所有分片成功发送，
事件才算送达。

单元测试和样本测试必须禁止意外网络请求。所有配置项检查和请求成功码应以实现时使用的
官方或已锁定接口约定为准。命令行约定：所有配置检查和所需投递成功时返回退出码 0；
配置错误返回 2；运行、解析、状态发布或通知失败返回 3。`dry-run` 将确定性的脱敏 JSON
差异输出到标准输出，使用相同退出码，但不得写入状态或联系飞书。

项目使用代码格式化与检查工具、静态类型检查和 pytest。具体工具与阈值在实施计划中
确定，不引入不必要的框架复杂度。

到的变化，不保证商品一定可用，也不保证购买成功。

## 14. 验收标准

满足以下条件时，首个版本视为完成：

1. 实际执行一次全新 Fork 冒烟测试，并在发布检查清单记录通过结果。测试从已提交的示例
   配置开始，只添加 `FEISHU_WEBHOOK_URL` Secret 和 Actions 写权限，手动运行工作流，
   成功创建 `monitor-state` 并静默建立基线，不需要修改运行器文件。
2. 使用临时状态目录执行基于 HTML 样本的命令行集成测试，断言退出码以及脱敏后的
   JSON/飞书消息内容；在完全不访问真实网络的前提下识别商品新增、下架、补货、售罄、
   改名和改价。
3. 样本序列证明：可疑的空解析或找不到分类时会保留商品状态；明确的零商品需要连续两次
   观察；异常提醒在连续失败第 1、3、12 次产生；下一次成功时只产生一条恢复提醒。
4. 模拟飞书和 Git 发布测试证明：静默基线和无变化行为正确；启动时使用不可变多分片
   内容重试；总是先处理最早的待处理事件；投递失败后快照已推进但事件仍待处理；正确
   校验成功响应体；支持消息拆分和至少一次事件 ID；处理两个发布阶段的预期父提交冲突；
   正确处理存在待处理事件的 `dry-run` 和冲突后发现旧事件的中止行为；失败时返回退出码
   3；日志和输出不包含 Secret。
5. CI 在不访问真实网络、不使用 Secret 的情况下，通过格式检查、代码检查、静态类型检查
   和全部自动化测试。
6. 静态工作流测试验证：任务有明确超时；定时与手动任务共享固定并发组；权限最小化；
   Pull Request 任务不接触 Secret；使用独立状态工作树并支持首次初始化；文档明确说明
   每 5 分钟为尽力执行，而非精确保证。
